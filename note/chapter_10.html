SECTION 02

软件系统质量属性

开发期 vs 运行期 · 口诀记忆 · 易混淆辨析 · 考点密度 ★★★★

📊1.1 质量属性两大分类 必考
通俗理解：买车的两套评价标准
开发期质量属性就像车的"好不好修、能不能改装"——评价的是开发、测试、维护的便利性。运行期质量属性就像"跑得快不快、安不安全"——评价的是系统实际运行的表现。
🔑 速记口诀
开发期：易扩重测维移（易理解性 · 可扩展性 · 可重用性 · 可测试性 · 可维护性 · 可移植性）
运行期：性安伸互可鲁（性能 · 安全性 · 可伸缩性 · 互操作性 · 可靠性/可用性 · 鲁棒性）
开发期质量属性
易理解性代码逻辑清晰，易于理解
可扩展性加功能，不影响现有结构
可重用性模块可在其他项目复用
可测试性便于验证正确性
可维护性发现问题、修复问题容易
可移植性迁移到不同平台成本低
运行期质量属性
性能处理时间·吞吐量
安全性合法访问+阻止非法访问
可伸缩性加资源，适应负载变化
互操作性与其他系统协同工作
可靠性/可用性无故障·时间占比
鲁棒性= 容错性 = 健壮性
⚠️ 三大易错点：① 可扩展性（加功能）≠ 可伸缩性（加资源）② 可用性（时间占比）≠ 可靠性（持续无故障）③ 鲁棒性 = 容错性 = 健壮性，三者同义！
概念公式/定义记忆点
可用性正常运行时间 / 总时间强调「时间占比」，如99.9%
可靠性持续无故障运行能力强调「持续无故障」
可扩展性增加新功能的容易程度「扩」= 扩充功能
可伸缩性增加资源适应负载的能力「伸」= 伸展规模
鲁棒性在异常条件下继续运行= 容错 = 健壮
📋 配套例题 1
以下属于开发期质量属性的是（　）
✅ 答案：B
可维护性属于开发期质量属性。性能、安全性、可用性都属于运行期质量属性。口诀「易扩重测维移」中的"维"就是可维护性。
📋 配套例题 2
软件系统在一定时间内正常工作的时间所占比例，指的是（　）
✅ 答案：B
可用性 = 正常运行时间 / 总时间，强调时间占比（如99.9%）。可靠性强调"持续无故障"，侧重质量而非比例。
📋 配套例题 3
某系统通过增加服务器节点来应对用户访问量的增长，该系统具备良好的（　）
✅ 答案：C
通过增加资源（服务器节点）来应对负载增长，这是可伸缩性（加资源）。注意与可扩展性（加功能）区分！
🏛️1.2 面向架构评估的质量属性 必考
通俗理解：买房的七大关注点
地段好（性能）、建筑质量过硬（可靠性）、门禁森严（安全性）、可以改造装修（可修改性）、功能设施齐全（功能性）、风格可以变化（可变性）、交通配套齐备（互操作性）。
🔑 速记口诀
「性可安可功可互」
性能 · 可靠性 · 安全性 · 可修改性 · 功能性 · 可变性 · 互操作性
质量属性核心含义子属性/注意
性能效率指标：处理时间、吞吐量响应时间 · 资源利用率
可靠性容错（自动修正）+ 健壮性（忽略错误继续运行）容错≠健壮性，前者修正后者忽略
安全性合法用户正常服务 + 阻止非法访问机密性·完整性·可用性
可修改性可维护性 + 可扩展性 + 结构重组 + 可移植性四个子属性，是最大的"属性家族"
功能性系统完成预期工作的能力功能正确性·完备性
可变性架构经扩展修改后仍符合规范不影响系统整体结构
互操作性与其他系统交互工作的能力标准接口·数据格式
💡 可修改性是个"大家族"，包含4个子属性：可维护性（改现有）、可扩展性（加功能）、结构重组（调整结构）、可移植性（迁移平台）
📋 配套例题
面向架构评估的质量属性中，"可修改性"包含的子属性不包括（　）
✅ 答案：C
可修改性的4个子属性：可维护性·可扩展性·结构重组·可移植性。可伸缩性是运行期质量属性（加资源应对负载），不是可修改性的子属性！这是高频陷阱。
SECTION 03

质量属性提升策略

可用性 · 性能 · 可修改性 · 安全性 · 四大策略族 · 考点密度 ★★★★★

🛡️2.1 可用性提升策略 高频
通俗理解：医院急救体系
首先能发现病人有问题（错误检测），然后能抢救回来（错误恢复），最好是提前预防不生病（错误避免）。
🔍 错误检测
  • 心跳（Heartbeat）
  • Ping / Echo
  • 异常检测
🔄 错误恢复
  • 表决（投票冗余）
  • 主动冗余（热备）
  • 被动冗余（冷备）
  • 检查点 / 回滚
🚫 错误避免
  • 服务下线维护
  • 事务（原子性）
  • 进程监控器
⚠️ 陷阱：「高内聚低耦合」是提升可修改性的策略，不是可用性！
📋 配套例题
以下不属于提升可用性策略的是（　）
✅ 答案：C
高内聚低耦合是提升可修改性策略中「局部化修改」的手段。心跳(错误检测)、主动冗余(错误恢复)、检查点回滚(错误恢复)都是可用性策略。
⚡2.2 性能提升策略
通俗理解：餐厅提升翻台效率
减少每道菜的烹饪时间（减少资源需求）、多雇厨师同时开灶（并发机制）、增加厨房设备（增加资源）、规定上菜优先顺序（资源仲裁）。
📉 资源需求
  • 减少计算量/中间数据
  • 减少处理事件数量
  • 限制执行时间
  • 控制采样频率
🔧 资源管理
  • 并发机制（多线程）
  • 增加资源（CPU/内存/带宽）
  • 维护多个副本（缓存）
⚖️ 资源仲裁
  • 先来先服务（FCFS）
  • 固定优先级调度
  • 动态优先级（轮询/最早截止）
📋 配套例题
以下不属于提升性能策略的是（　）
✅ 答案：D
主动冗余（热备）是提升可用性（错误恢复）的策略。并发机制（资源管理）、增加资源（资源管理）、固定优先级（资源仲裁）都是性能策略。
🔧2.3 可修改性提升策略 高频
通俗理解：装修房子的哲学
「局部化修改」= 把相关的东西都放一个房间（高内聚），不同房间尽量独立（低耦合）。「防止连锁反应」= 不要让拆一面墙导致整栋楼垮掉（信息隐藏）。「推迟绑定」= 装修风格留到入住时再定（运行时配置）。
🎯 局部化修改
  • 高内聚低耦合
  • 预测变更（封装变化点）
  • 模块通用化
🔒 防止连锁反应
  • 信息隐藏
  • 维持接口稳定
  • 限制通信路径
  • 使用中介（Broker）
⏳ 推迟绑定时间
  • 运行时注册
  • 多态
  • 配置文件
  • 插件机制
⭐ 记忆技巧：「防止连锁反应」中的信息隐藏是最重要的手段，也是高内聚低耦合的底层原理。
📋 配套例题
以下属于提升可修改性策略中「防止连锁反应」的是（　）
✅ 答案：B
信息隐藏属于「防止连锁反应」策略。高内聚低耦合和预测变更是「局部化修改」策略，运行时注册是「推迟绑定时间」策略。
🔐2.4 安全性提升策略
通俗理解：银行的三道防线
第一道：门禁+身份认证（抵抗攻击）；第二道：报警系统（检测攻击）；第三道：保险柜+报警后恢复（从攻击中恢复）。
🛡️ 抵抗攻击
  • 用户身份验证（Authentication）
  • 授权（Authorization）
  • 数据机密性（加密）
  • 限制暴露面（最小权限）
🚨 检测攻击
  • 入侵检测系统（IDS）
  • 审计日志
🔁 从攻击中恢复
  • 恢复系统状态
  • 识别攻击者
📋 配套例题
以下属于提升安全性策略中「抵抗攻击」的是（　）
✅ 答案：C
用户身份验证（Authentication）属于「抵抗攻击」策略。入侵检测系统属于「检测攻击」，恢复系统状态和识别攻击者属于「从攻击中恢复」。
SECTION 04

质量属性场景描述

六大要素 · 场景类型识别 · 例题实战 · 考点密度 ★★★★★

🎯3.1 场景六要素 必考
通俗理解：描述一次交通事故
谁（司机=刺激源）→ 做什么（急刹车=刺激）→ 在什么情况下（雨天路滑=环境）→ 对什么（汽车=制品）→ 产生什么结果（停车=响应）→ 如何度量（刹车距离20米=响应度量）
🔑 速记口诀
「源刺环制响度」
刺激源（Source）· 刺激（Stimulus）· 环境（Environment）· 制品（Artifact）· 响应（Response）· 响应度量（Measurement）
① 刺激源 产生刺激的人、系统或其他实体（如"用户"、"黑客"、"第三方系统"）
② 刺激 到达系统时需要考虑的条件（如"发出支付请求"、"发起注入攻击"）
③ 环境 刺激发生时系统所处的状态（如"正常运行"、"高峰负载"、"网络故障"）
④ 制品 被刺激的对象（整个系统、某个模块、数据、进程等）
⑤ 响应 系统接收刺激后采取的行动（如"完成支付"、"拒绝访问"、"切换备用系统"）
⑥ 响应度量 对响应的量化方式（如"10秒内"、"99.9%可用性"、"4人·月"）
场景类型快速识别
场景类型关键词典型响应度量
性能响应时间·吞吐量·高峰负载X毫秒内·每秒N个请求
可用性故障恢复·冗余·99.X%X秒内恢复·N%可用时间
安全性身份验证·加密·攻击·非法访问访问被拒绝·攻击被识别
可修改性修改工作量·人·月·代码行数X人·月内完成·影响N个模块
📋 配套例题 1
质量属性场景描述的6个要素中，不包括（　）
✅ 答案：C
场景6要素：刺激源·刺激·环境·制品·响应·响应度量。「成本」不是6要素之一，「成本效益」是CBAM评估方法关注的内容。
📋 配套例题 2
"在高峰负载情况下，用户发起支付请求后，系统必须在10秒内完成支付功能" —— 该场景属于（　）质量属性
✅ 答案：A
关键词：「高峰负载」（环境）+「10秒内完成」（响应度量），是对响应时间的要求，属于性能质量属性场景。
📋 配套例题 3
"系统需要对Web界面风格进行修改，修改工作必须在4人·月内完成" —— 该场景属于（　）质量属性
✅ 答案：D
关键词：「修改」+「4人·月」（工作量度量），是对修改成本的要求，属于可修改性质量属性场景。
SECTION 05

架构评估核心概念

敏感点 · 权衡点 · 风险 · 非风险 · 场景辨析实战 · 考点密度 ★★★★★

⚖️4.1 四大核心概念辨析 必考
通俗理解：开车的类比
油门（只影响速度）= 敏感点 | 空调（影响舒适度和油耗）= 权衡点 | 刹车失灵（危险决策）= 风险 | 定期保养（良好决策）= 非风险
🎯 敏感点（Sensitivity Point）
影响某一个质量属性的关键架构决策
例：改变处理器速度 → 只影响性能
⚖️ 权衡点（Tradeoff Point）
影响多个质量属性的敏感点
例：加密 → 同时影响安全性和性能
⚠️ 风险（Risk）
有问题的架构决策，可能导致潜在故障
例：紧耦合 → 难以修改
✅ 非风险（Non-Risk）
良好的架构决策，分析后认为可接受
例：合理的响应时间设定
🔑 辨析速记
看「影响几个」：影响1个质量属性 → 敏感点；影响多个质量属性 → 权衡点
看「有没有问题」：有问题/隐患 → 风险；合理决策 → 非风险
四大概念辨析例题解析
场景描述答案核心判断依据
改变业务数据编码方式会对系统的性能和安全性产生影响权衡点影响"性能"和"安全性"两个属性 → 多个 = 权衡点
假设用户请求频率每秒1个，响应时间设定为1秒是可以接受的非风险合理的、经过分析可接受的决策 → 非风险
对交易请求处理时间的要求将影响数据传输协议和处理过程的设计敏感点只影响"性能"这一个质量属性 → 敏感点
系统的支付部分与第三方平台紧耦合，需要支持新平台时会导致大量修改风险存在隐患（紧耦合），影响可修改性 → 风险
系统拟采用新加密算法，会提高安全性，但降低性能权衡点影响"安全性"和"性能"两个属性 → 多个 = 权衡点
📋 配套例题 1
影响多个质量属性的敏感点称为（　）
✅ 答案：D
权衡点是影响多个质量属性的敏感点。敏感点只影响一个质量属性；权衡点是敏感点的特殊情况（影响多个）。
📋 配套例题 2
"改变业务数据编码方式会对系统的性能和安全性产生影响"是对（　）的描述
✅ 答案：D
影响"性能"和"安全性"两个质量属性 → 多个属性 → 权衡点。记住：权衡 = 权衡多个利益（多个属性）。
📋 配套例题 3
"假设用户请求频率为每秒1个，业务处理时间小于30毫秒，则将请求响应时间设定为1秒是可以接受的"是对（　）的描述
✅ 答案：B
这是一个经过分析后认为合理、可接受的架构决策，属于非风险。关键词：「可以接受的」→ 非风险（良好决策）。
SECTION 06

SAAM — 软件架构分析方法

最早评估方法 · 主关注可修改性 · 5步流程 · 考点密度 ★★★

🔍5.1 SAAM 方法详解
通俗理解：新房验收
先看设计图（架构描述），再模拟各种使用场景（场景开发），逐个检查每个场景（单个场景评估），观察场景间是否互相影响（场景交互），最后给出整体报告（总体评估）。
SAAM = Software Architecture Analysis Method 输入：① 问题描述 ② 需求说明 ③ 架构描述 主要分析内容：可修改性（主要） 评估技术：场景技术
SAAM 五步流程
🗺️ 五步执行顺序（口诀：场架单交总）
1场景开发：收集和提炼系统任务场景，确定需要分析的使用场景
2架构描述：以相关涉众能理解的方式描述候选架构
3单个场景评估：逐一评估每个场景对架构的影响（直接/非直接支持）
4场景交互：识别场景共享的架构构件，分析场景间的相互影响
5总体评估：综合分析，给出权重和最终评价
🔑 口诀
「场架单交总」 — 场景开发 → 架构描述 → 单个评估 → 场景交互 → 总体评估
📋 配套例题 1
SAAM方法主要分析的质量属性是（　）
✅ 答案：B
SAAM 是最早的架构评估方法，主要分析可修改性，通过场景技术评估修改对架构的影响程度。
📋 配套例题 2
SAAM方法五步过程的正确顺序是（　）
✅ 答案：B
SAAM五步：场景开发 → 架构描述 → 单个场景评估 → 场景交互 → 总体评估。口诀「场架单交总」帮助记忆顺序。
SECTION 07

ATAM — 架构权衡分析法

多质量属性权衡 · 效用树 · 4阶段9步骤 · 考点密度 ★★★★★

🏆6.1 ATAM 方法概述 必考
通俗理解：买车综合评估
ATAM像一个专业购车顾问，帮你在性能、安全、省油、舒适等多个维度之间找到最佳平衡点，而不是只看某一个指标。
ATAM = Architecture Tradeoff Analysis Method 核心目标：确定多个质量属性之间的折中（Tradeoff） 关注的质量属性：性能 · 可用性 · 安全性 · 可修改性（4个） 核心工具：效用树（Utility Tree） 评估技术：场景技术 + 启发式分析
⚠️ 高频考点：效用树关注的4个质量属性是「性能·可修改性·可用性·安全」，不包含可测试性、互操作性等！
📋6.2 ATAM 四阶段详解 必考
🔑 口诀
「演调测报」 — 演示 → 调查和分析 → 测试 → 报告
🎭 阶段1：演示（3步骤）
1介绍ATAM方法本身
2介绍业务驱动因素（系统目标、约束、重要需求）
3介绍要评估的体系结构（候选架构）
🔬 阶段2：调查和分析（3步骤）
4确定架构方法（识别主要的架构决策）
5生成质量属性效用树（对质量属性分类和优先级排序）
6分析体系结构方法 → 找出风险·非风险·敏感点·权衡点
🧪 阶段3：测试（2步骤）
7头脑风暴和优先场景（更广泛的涉众参与）
8分析架构方法（针对优先场景再次分析）
📊 阶段4：报告（1步骤）
9提供评估期间收集的所有信息（结果报告给涉众）
⭐ 重点：风险·非风险·敏感点·权衡点 是在阶段2第6步（分析体系结构方法）中被识别的！
⭐ 重点：效用树 是在阶段2第5步生成的，是ATAM的核心工具！
📋 配套例题 1
ATAM方法的评估过程不包括（　）阶段
✅ 答案：C
ATAM四阶段：演示·调查和分析·测试·报告。没有「实施」阶段，ATAM是评估方法而非实施方法。口诀「演调测报」！
📋 配套例题 2
ATAM方法中，用于对质量属性进行分类和优先级排序的工具是（　）
✅ 答案：B
效用树（Utility Tree）是ATAM的核心工具，在"调查和分析"阶段第5步生成，用于对质量属性进行分类、细化和优先级排序。
📋 配套例题 3
以下不属于ATAM效用树关注的质量属性的是（　）
✅ 答案：C
效用树关注4个质量属性：性能·可修改性·可用性·安全。可测试性不在其中！口诀「性可用安」帮助记忆。
🔄6.3 SAAM vs ATAM 全面对比 高频
🔑 一句话区分
SAAM改单个（可修改性）· ATAM折多个（性·用·安·改）
对比项SAAMATAM
特定目标验证体系结构，发现潜在问题确定多个质量属性之间的折中
主要质量属性可修改性（主要）性能·可用性·安全性·可修改性
评估技术场景技术场景技术 + 启发式分析
核心工具场景分析效用树（Utility Tree）
知识库可复用性不涉及有基于属性的体系模型，可复用
是否找权衡点否是（核心输出之一）
📋 配套例题
SAAM和ATAM都使用的评估技术是（　）
✅ 答案：A
SAAM和ATAM都使用场景技术。ATAM在场景技术基础上还增加了启发式分析（B是ATAM独有的）。

其他架构评估方法

CBAM · SAEM · SAABNet 等 · 了解特点 · 考点密度 ★★

📚7.1 其他评估方法汇总
记忆技巧：成本效益CBAM打头，其他七兄弟各有专长
方法全称/特点核心关注
