SECTION 01

软件架构演化与定义的关系

三大要素 · 增删改本质 · 演化目的 | 考试权重 ★★

🌱1.1 软件架构三大要素与演化本质 必考
生活类比：装修房子
刚搬进去是毛坯（初始架构），随着家庭成员变化（需求变化），需要打隔断、加家具、改水电（演化），但又不能动承重墙（保持主体稳定）。软件架构演化就是对三大要素的持续优化过程。
软件架构三大要素： ① 组件（Component） → 系统的功能单元 ② 连接件（Connector） → 组件间的交互机制 ③ 约束（Constraint） → 组件与连接件的配置规则 演化的本质 = 对三大要素的 添加（A）· 修改（M）· 删除（D） 演化目的 = 适应环境变化 + 满足用户需求变化
⚠️ 演化关注的是三大要素的"增删改"，不是"查"。演化不仅仅是修 Bug，更是主动适应变化！
🧠 速记口诀
「组连约，加改删」
谐音故事：祖父（组）练功（连）每月（约），家（加）里改（改）了三（删）次——祖父练功每月一次，家里改造三次
📋 配套例题
软件架构演化主要关注组件、连接件和约束的（　）
✅ 答案：D
演化是对三大要素（组件、连接件、约束）的全方位操作，包括添加、修改和删除三种操作，缺一不可。只选A、B或C都是不完整的。
SECTION 02

面向对象软件架构演化过程

对象·消息·复合片段·约束 | 操作符辨析 ★★★

🔧2.1 四类演化操作概览 理解
微信群类比
对象 = 群成员，消息 = 聊天记录，复合片段 = 话题分组（如"#公告"），约束 = 群规。对群的所有管理操作正好对应演化的四类。
演化类型操作符含义记忆提示
对象演化 AO Add Object — 添加对象 A=Add，O=Object
DO Delete Object — 删除对象 D=Delete，O=Object
消息演化 AM Add Message — 添加消息 A=Add，M=Message
DM Delete Message — 删除消息 D=Delete
SMO Swap Message Order — 交换两条消息的时间顺序 S=Swap，Order顺序
OM Overturn Message — 反转消息的发送方与接收方 O=Overturn 反转
CMM Change Message Module — 改变消息的发送或接收对象 C=Change，Module=对象
复合片段演化 AF Add Fragment — 添加复合片段 F=Fragment
DF Delete Fragment — 删除复合片段 D=Delete
FTC Fragment Type Change — 改变复合片段类型 T=Type 类型
FCC Fragment Condition Change — 改变复合片段条件 C=Condition 条件
约束演化 AC Add Constraint — 添加约束 C=Constraint
DC Delete Constraint — 删除约束 D=Delete
⚠️ 极易混淆三兄弟：SMO（交换顺序）· OM（反转发送/接收方）· CMM（改变发送或接收对象）——方向不同，性质完全不同！
🧠 速记口诀
「对消片约，各有增删」
消息5操作：AM加 · DM删 · SMO换序 · OM反转 · CMM改对象
关键：OM=反转发接双方；CMM=换掉其中一方
📋 配套例题 1
在面向对象软件架构演化中，"反转消息的发送对象与接收对象"属于（　）操作
✅ 答案：B
OM = Overturn Message，即将发送方与接收方对调（A→B 变成 B→A）。SMO是交换两条消息的时间顺序（谁先谁后），CMM是把发送方或接收方换成另一个对象（A→B 变成 A→C）。三者方向不同！
📋 配套例题 2
复合片段演化中，"改变复合片段类型"属于（　）操作
✅ 答案：C
FTC = Fragment Type Change，改变复合片段的类型（如把 alt 改成 opt）。FCC = Fragment Condition Change，改变复合片段的条件（如把 [x>0] 改成 [x>=0]），是改条件不是改类型。
SECTION 03

软件架构演化方式分类

静态演化 · 动态演化 · 演化时期 | 考试权重 ★★★

🕒3.1 软件架构演化时期（4个）高频
建筑工程类比
设计时演化=图纸改设计；运行前演化=交房前改装修；有限制运行时演化=按消防规定改造；运行时演化=不停电改线路（最难最贵）。
演化时期时间点特点
① 设计时演化代码编译之前成本最低，最灵活，推荐优先
② 运行前演化编译之后、执行之前编译完成但未启动时修改
③ 有限制运行时演化满足特定约束条件时预设演化条件，安全可控
④ 运行时演化系统运行中无法满足要求时代价最高，风险最大
🧠 速记口诀
「设运限运」→ 谐音"设运限运（是云海运）"
设计时→运行前→有限制运行时→运行时，按时间顺序递进，代价逐步升高
📋 配套例题
"发生在代码编译之后、系统执行之前"的演化时期是（　）
✅ 答案：B
运行前演化的时间点精确定义：编译完成之后、系统执行之前。设计时演化是编译前；有限制运行时是有条件约束的运行时演化；运行时演化是系统运行过程中的实时演化。
🔄3.2 静态演化 vs 动态演化 陷阱题
🏪 静态演化（停机改造）

风险较低，可充分测试

类比商场不打烊换装饰
时机系统持续运行中
风险较高，需精心设计
代价技术复杂度成本

② 行为变化

📋 配套例题

✅ 答案：D
动态演化的四类内容是：属性改名、行为变化、拓扑结构改变、风格变化。"格式变化"是干扰项，没有"格式变化"这个类别！这是历年真题的经典陷阱，务必牢记。

🧠 速记口诀（18条）
「成进风主总平，目模影复构重，遵新环标质需」
故事：成精的疯子（成进风）主播总评价（主总平），目睹模仿影帝复购充值（目模影复构重），尊重新环保质量需求（遵新环标质需）
⭐4.2 高频考点：平滑演化 vs 主体维持 历年必考
🌊 平滑演化
关键词演化速率稳定
表现相邻版本更新率相对稳定
度量看版本之间的变化量
类比匀速行驶，不忽快忽慢
🏛️ 主体维持
关键词平均增量稳定
表现系统主体行为保持稳定
度量看系统总量增长的平均值
类比孩子每年稳步成长
⚠️ 考试做题：看到"速率稳定/版本更新率"→ 平滑演化；看到"增量稳定/主体行为"→ 主体维持。两者一字之差，答案相反！
📋 配套例题 1
在软件系统的生命周期里，软件的演化速率趋于稳定，如相邻版本的更新率相对稳定。这描述的是（　）原则
✅ 答案：C
关键词"演化速率"、"版本更新率稳定" → 平滑演化。若题目改为"平均增量稳定"或"主体行为稳定"则是主体维持。这两个原则是本章最高频的混淆考点！
📋 配套例题 2
"软件演化的平均增量须保持平稳，保证软件系统主体行为稳定"是（　）原则
✅ 答案：A
关键词"平均增量稳定"、"主体行为稳定" → 主体维持。注意与平滑演化的区别：平滑演化强调速率，主体维持强调增量和行为。
SECTION 05 ★★★

大型网站系统架构演化实例

10阶段演化路径 | 案例题·论文必备，餐厅发展史类比

🌐5.1 十阶段演化路径（完整版）
餐饮连锁发展史类比
从夫妻小店（单体）→ 前厅后厨分离（垂直）→ 备菜（缓存）→ 多家分店（集群）→ 收银分台（读写分离）→ 外卖前置点（CDN）→ 不同菜系分别采购（分布式）→ 智能点餐（NoSQL）→ 拆分品牌线（业务拆分）→ 中央厨房+加盟体系（微服务）
1
单体架构
应用、数据库、文件全部在1台服务器上
夫妻小店，啥都自己来
2
垂直架构
应用服务器 + 文件服务器 + 数据服务器，3台分离
前厅后厨分开，专人专事
3
使用缓存
本地缓存 + 分布式缓存，减少数据库压力
备菜柜，常用食材提前备好
4
服务集群
负载均衡 + 应用服务器集群，横向扩容
开了多家分店，分流客人
5
数据库读写分离
主库写、从库读，主从复制机制同步
账房先生专管开单，收银台专管收钱
6
反向代理 + CDN 易混淆
CDN在网络提供商机房；反向代理在网站中心机房；原理相同，都是缓存
社区设外卖自提点（CDN），店内设叫号台（反向代理）
7
分布式文件系统 + 分布式数据库
业务分库，不同业务数据单独存储
川菜、粤菜分别采购，互不干扰
8
NoSQL + 搜索引擎
处理海量非结构化数据，提升查询效率
智能点餐系统，大数据推荐菜品
9
业务拆分
大应用拆分为多个独立的子应用，各自部署
拆分成独立品牌线（正餐/快餐/外卖）
10
分布式服务（SOA/微服务）
公共业务抽取为服务，各应用调用，形成服务中心
中央厨房 + 加盟体系，统一配送，各店调用
🧠 速记口诀（10阶段）
「单垂缓集读，反分N拆分」
单（单体）→垂（垂直）→缓（缓存）→集（集群）→读（读写分离）→反（反向代理CDN）→分（分布式文件/数据库）→N（NoSQL+搜索）→拆（业务拆分）→分（分布式服务）
⚠️ CDN vs 反向代理：都是缓存，但位置不同！CDN在网络提供商机房（离用户近），反向代理在网站中心机房（离服务器近）。
📋 配套例题
关于大型网站架构演化中的CDN和反向代理，下列说法正确的是（　）
✅ 答案：A
CDN和反向代理的基本原理都是缓存。位置区别：CDN部署在网络提供商机房（靠近用户），反向代理部署在网站中心机房（靠近服务器）。B、C说反了，D完全错误。
SECTION 06

软件架构维护

三大管理 · 6个度量指标 · 构件管理陷阱 | 考试权重 ★★

🛠️6.1 维护过程三大管理 陷阱题
图书馆类比
知识管理 = 图书分类编目；修改管理 = 版本修订（修改区域隔离）；版本管理 = 不同版次的书。注意：没有"构件借阅管理"这回事！
管理类型核心内容关键点
① 架构知识管理 管理架构知识 = 架构设计 + 架构设计决策 决策也是知识的一部分！
② 架构修改管理 建立隔离区域，将修改影响降到最小 隔离区域是核心机制
③ 架构版本管理 记录架构变更历史，为演化提供可靠依据 版本是演化的基础
⚠️ 最高频陷阱：维护过程不包括"架构构件管理"！选到"构件管理"就错了。三大管理是：知识·修改·版本。
🧠 速记口诀
「知修版」→ 谐音"智修板"
智者（知识管理）修（修改管理）板子（版本管理）——只有三块板，没有第四块"构件板"！
📋 配套例题
软件架构维护过程不包括（　）
✅ 答案：D
维护过程仅包含三大管理：知识管理、修改管理、版本管理。"架构构件管理"不是维护过程的组成部分，是本章最经典的高频干扰项！
📊6.2 可维护性6个度量指标 理解
指标名称缩写度量内容
圈复杂度CNN程序逻辑复杂程度（分支越多越复杂）
扇入扇出度FFC模块被调用次数（扇入）和调用其他模块数（扇出）
模块间耦合度CBO模块与其他类的耦合程度
模块的响应RFC接收到消息后可能执行的方法数
紧内聚度TCC直接共享方法比例（紧密内聚）
松内聚度LCC直接或间接共享方法比例（宽松内聚）
⚠️ 干扰项：代码行数（LOC）不属于6个可维护性度量指标！LOC是软件规模指标。
🧠 速记口诀
「圈扇耦响紧松」→ 谐音"圈扇藕响紧松"
圈（CNN圈复杂度）扇（FFC扇入扇出）藕（CBO耦合度）响（RFC响应）紧（TCC紧内聚）松（LCC松内聚）——共6个，没有LOC！
📋 配套例题
以下不属于架构可维护性度量指标的是（　）
✅ 答案：D
6个可维护性指标口诀"圈扇耦响紧松"：CNN、FFC、CBO、RFC、TCC、LCC。代码行数（LOC）是软件规模指标，不是可维护性度量指标。
